# 02 - Triton & TileLang

Topic 01's problems rewritten in tile DSLs, to see what the compiler takes over. Short version: in Triton/TileLang I never write thread indices or bounds checks, I only pick tile sizes and the math. Swapping the elementwise formula in a kernel means changing one line, not touching the data movement.

## What's here

```
kernels/          triton_vector_add, triton_fused_op, triton_softmax
                  tilelang_scale_add, tilelang_copy2d, tilelang_softmax
matmul_ladder/    one GEMM four ways: naive.cu -> triton.py -> tilelang.py -> cuBLAS
lowering_study/   the same TileLang GEMM compiled to sm_90a vs sm_100a, outputs side by side
tests/            pytest, 19 tests
```

## The matmul ladder

This started as "write a naive CUDA matmul" and turned into tuning one. All on my 3060 laptop, 2048^3 fp16 unless noted.

Naive CUDA (1024^3 fp32, block size sweep, 3 runs each because the laptop's thermals make single runs jump around):

| BS | GFLOPS |
| --- | --- |
| 8 | ~520 (always worst, 64 threads just can't keep enough loads in flight) |
| 16 | ~600 |
| 32 | ~625 |

Naive is ~50x below cuBLAS. The gap is everything at once: tensor cores, data reuse, pipelining.

Triton (tuned configs):

| config (BMxBNxBK) | TFLOPS |
| --- | --- |
| 32x32x32 | 15.0 |
| 64x64x32 | 17.6 |
| 128x64x32 | 25.7 |
| 128x128x32 | 20.7 |
| 128x128x64 | 23.1 |
| 64x64x64 | 18.3 |
| torch (cuBLAS) | 26.9 |

Best Triton config reaches 25.7 TFLOPS, 96% of cuBLAS, with about 30 lines of Python. Tiling + tl.dot is where the money is.

TileLang (measured on TileLang 0.1.14; two consecutive runs agreed within ~5%, the spread between runs is shown):

| config (BM,BN,BK,threads,stages) | TFLOPS |
| --- | --- |
| 64,64,32,128,1 | 17-18 |
| 64,64,32,128,3 | 17-18 |
| 128,128,32,128,3 | 25.4-26.7 |
| 128,128,64,256,3 | ~24 |
| 128,256,64,256,3 | skipped at launch: wants 144 KB dynamic smem, this card caps at 100 KB |

This table is a small research finding by itself. On TileLang 0.1.12 the same four configs topped out at 19.1 TFLOPS, well behind Triton, and my conclusion then was "TileLang makes me place shared tiles and stage counts by hand; Triton hands that to the compiler and just works." After upgrading to 0.1.14 the best config reaches cuBLAS parity (~26 of 26.9 TFLOPS) with zero changes to my kernel code. So the DSL's maturity moved the result by ~35%, and "finer control vs faster" turned out to be about the codegen version, not a property of the DSL. Worth pinning your DSL version in the README of anything you benchmark.

## Softmax

`tilelang_softmax.py` and `triton_softmax.py`: one block per row, width rounded up to a power of 2 with -inf padding, max subtracted before exp (the tests include inputs x1000, unstable versions produce inf/nan). Timed against torch.softmax at M=4096:

| N | mine (us) | torch (us) |
| --- | --- | --- |
| 256 | 45.8 | 52.9 |
| 1024 | 115.3 | 115.3 |
| 4096 | 563.4 | 574.7 |

At N=4096 this moves ~238 GB/s against the ~250 GB/s this card measures for pure streaming, so it's about saturated. A read-once + row-reduce + write-once kernel is bandwidth-bound, and at N=256 rows are only 1 KB so scheduling overhead takes a bigger bite.

## The lowering study (lowering_study/)

I compiled the same `T.gemm` kernel (64x64x32, 3 stages) with TileLang to two targets and read the generated CUDA side by side. I did this after hand-writing tensor core GEMM paths in topics 03-04, to see how much of that a DSL would have done for me. Run on TileLang 0.1.14.

| | sm_90a | sm_100a |
| --- | --- | --- |
| tensor core instruction | wgmma (warpgroup) | mma.sync + ldsm, no tcgen05 |
| descriptors | host CUtensorMap for TMA, wgmma smem descriptors built in-kernel by the templates | none needed, ldmatrix addresses generated by templates |
| smem layout | decided in TileLang's layout pass, becomes 128B-swizzle TMA parameters | same layout pass, becomes the row layout ldmatrix wants |
| data into smem | TMA + mbarrier | TMA + mbarrier (upgraded from plain ld/st copies in TileLang 0.1.13) |

The DSL does handle most of the hard parts: which tensor core instruction to target, the swizzle layout, descriptor generation, TMA vs plain loads, mbarrier insertion. What it doesn't decide for me: tile sizes, stage count, thread count, the things you only get by measuring.

The interesting part is the sm_100a column. Between 0.1.13 and 0.1.14 the supply path caught up (plain ld.global/st.shared copies became real TMA + mbarrier), but the tensor core instruction is still the sm80-style mma.sync fallback. In other words, this DSL version cannot reach the tcgen05 instruction at all on the newest hardware - using it still means writing instruction-level code by hand. One environment note: TileLang calls whatever nvcc is on PATH, and sm_100a needs CUDA 13 there.

Regenerate the outputs with `python lowering_study/make_lowering.py` (needs the tilelang extra).
